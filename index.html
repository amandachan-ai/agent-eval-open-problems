Five Hard Problems in Evaluating AI Agents: Working Notes

For people who build LLM and agent evaluations: proactive triggers, multi-turn interaction, ground truth over large data, prompt changes that regress other cases, and rigorous experiments that yield only mild gains. Each problem is laid out as "common practice → where it falls short → better directions", followed by a feasibility tiering.

1. Bottom line

  • Freeze the scenario and the success criteria, not the verbatim answer or the verbatim dialogue. This one principle addresses proactive triggers, multi-turn interaction and large-scale ground truth.
  • Never look only at the average. A system prompt is a global parameter. Always report per-case flips (up / down / unchanged), and first learn how many cases flip when nothing changes.
  • Estimate the ceiling before investing; validate the instrument before optimizing. If the targeted issue is a small share of user dissatisfaction, or the judge disagrees with users, even a rigorous experiment can only buy a mild result.

2. Problem 1: Proactive agents — "it did not exist a second ago"

The input to a proactive agent is not "what the user asked" but "a message that just arrived". A correct evaluation must do two things: ① make the decision at the moment the message arrives, and ② use only information that existed at that moment. I call this as-of-T (point-in-time) evaluation. A traditional eval set, whose questions "were always there", simulates neither.

Hypothetical example: at T someone in a group chat writes "Can anyone take a look at this doc?", and a few minutes later a colleague replies "I'll do it". If the agent's retrieval during evaluation can see the later "I'll do it", it may answer "Great, it's yours" — something no one could know at T. And if "I'll do it" is used as the reference answer, we would wrongly conclude the agent should volunteer the user.

Common practice and its limits

The common practice is a single point-in-time snapshot: freeze the conversation before the trigger, add a fixed "current time", and ask the agent whether to act and what to say. Limits:

  1. It evaluates a moment, not timing. Too early, too late, repeated nudges, and how often the agent interrupts per day are all invisible.
  2. Future-information leakage. Most retrieval systems cannot "go back in time". Searching outputs for leaked strings afterwards cannot prove absence: future information changes tone, certainty and what gets omitted.
  3. The unit of evaluation does not match the product trigger. For example, the product fires only after a specific user gesture, while the dataset samples every message.
  4. Positives are rare. An agent that always stays silent can still score high accuracy.
  5. Hindsight bias in labels. Annotators see the whole conversation before deciding what should have happened at T.
  6. The real outcome arrives later. Whether a suggestion was accepted, or how much it was edited, is a delayed signal.

Better directions

ApproachHowCost
Stream replayFor every message, build the prefix "up to and including it", treat it as just arrived, and ask once. Metrics: per-arrival precision / recall, messages until first action, duplicate actions, interruptions per 100 messagesLow (any timestamped data works)
Minimal pairsThe same conversation with and without the trigger message — the decision must flip; add a distractor — the decision must not changeLow; no full gold needed
Time-fenced retrievalRetrieve only content created ≤ T; if that is impossible, claim only "present-day observation", never historical replayNeeds system support
Make the message truly appear at that secondPost messages one by one into a test environment; the last one is T; then trigger the agentHigh: environment pollution, indexing latency

3. Problem 2: Multi-turn interaction — can a static eval set still work?

Yes — it depends on what is static. Multi-turn evaluation mixes two questions:

QuestionSuitable setBlind spot
Given a correct history, is this turn right?Static transcripts (reproducible, cheap)How the agent recovers from its own mistakes
Did the whole interaction end with the job done?Static scenario + criteria, dynamic dialogue (simulated user or human)Verbatim reproducibility (compensate with repeated trials)

What if the answer itself evolves?

Once dialogue is dynamic, the "right answer" at turn 3 depends on what the agent said in turns 1 and 2, so verbatim answers cannot be stored in advance. Store what does not depend on the path instead: goals and end state (a transcript saying "done" does not count — check the environment), hidden facts (known to the user, to be elicited by the agent), must / must-not rules, and interaction constraints (e.g. finish within N turns). This also avoids penalizing solutions that are better for the user but unforeseen by the task author.

How to decide whether the eval set may evolve

Risks of a simulated user: the simulator makes its own mistakes (leaking hidden facts, breaking persona, giving up early), and those mistakes are charged to the agent — so the simulator must be evaluated too. Run each scenario k times; for features where users never see retries, report pass^k.

4. Problem 3: Data too large for any human to verify ground truth

To be realistic, test environments (a simulated organization with its messages and documents) often grow larger than anyone can read. Verification cost grows with the data; human understanding does not. As agents get stronger, their errors stop being "nonsense" and become fluent and plausible, but incomplete or mis-scoped — exactly the errors only someone familiar with the data can spot.

Typical failure patterns (hypothetical): the agent queries a channel, the tool returns "no messages", and instead of trying another query it fluently asserts "there is no relevant record"; or the gold answer cites a message that lies outside the time range the system can retrieve — an error in the ruler, not the agent.

ApproachWhat it does
Ground truth by constructionWrite a fact ledger first, then render it into data; gold is a ledger query. Needles / canaries can be planted too
Gold with provenanceEvery assertion carries a source id + quote; automatically check that the source is within the retrievable time range, indexed, and readable by the caller
Computable questionsAnswers such as "who mentioned Y in X during a period" are computed by code — a code oracle instead of an LLM judge
Perturbation testsChange one fact — the answer must change; add a distractor — it must not; remove the source — the agent must say it cannot find it
Micro-worldsEach scenario gets a small dataset one person can fully read, used to verify correctness; the large environment only tests robustness at scale and under noise
Spend humans on disagreementsOnly cases where judges disagree, or a judge disagrees with a code oracle, go to humans; add a stratified sample to estimate judge error and record inter-annotator agreement (IAA)
Verify the path firstexpected → retrieved → model-visible → answer; find the first divergence. Checking "was it retrieved" is far cheaper than checking a whole synthesis

What about real organizational data? It offers a realistic distribution, and the person asking usually knows the answer; the costs are privacy and compliance, irreproducibility, no gold, unshareable cases and selection bias. A workable split: real data to discover, synthetic data to regress — let data owners verify answers about their own data, and shrink each discovered failure into a minimal synthetic reproduction.

5. Problem 4: Fixing A with a prompt change breaks B

A system prompt is a global parameter: a sentence added to fix a few cases acts on every case. The average hides flips in both directions, and part of the churn is just generation randomness.

ApproachWhat it does
Per-case flips + slicesAlways report up / down / unchanged, split by language, tone, length and task type
Know the noise flip rateRun the same configuration twice (A/A) to get a baseline; flips count only above it
Pre-set a regression limit per sliceSet non-inferiority margins by user cost; a safety guardrail must be able to veto, not just be "reported"
Narrow the blast radiusRoute the new prompt only where the evidence covers; other paths must render byte-identical prompts, locked by hash tests
Separate dev and held-out setsA dev set whose failures you can read vs a held-out set you cannot; no held-out gain, no credit
Fix causes, not casesRemove the general rule that causes the problem rather than patching exceptions for individual failures

6. Problem 5: A rigorous experiment, a mild improvement

A common situation: you find a root cause from negative user feedback, change the prompt, and run the experiment properly — pre-registration, a held-out set, repeated generations, multi-vote judging, a permutation test — and get a statistically significant gain on the targeted issue, while overall user satisfaction barely moves. The experiment was not wrong; the causes are structural:

CauseWhat happensNext time
The target is only part of the dissatisfactionThe fixed issue is a small slice of negative feedback, which caps the overall impactEstimate the ceiling first: share × fixable fraction
Most cases do not moveSignificance does not mean most cases changed; only a few may flipReport per-case flips, not just a p-value
Judge and users disagreeFor example, the judge rewards longer, more thorough answers while users prefer shorter onesValidate the instrument first: a judge that sees only the input, not the output, as a control — if it predicts user feedback equally well, the judge is not measuring output quality
Confounders invert the conclusionFor example, request difficulty drives both answer length and user rating, so "longer answers are rated worse" may be an artifactStratify by the confounder
Generation noise ≈ effect sizeReruns of the same configuration differ by about as much as the effect; repeating the judge does not help, only repeating generation doesMultiple generations per arm; compute power in advance and accept "inconclusive"
A model upgrade swamps the promptThe model changes mid-experiment; old evidence no longer transfers, and the new model's own gain dwarfs the prompt'sTie evidence to the model version; if an upgrade is scheduled, test on the new model or wait
User feedback is sparse and slowFew ratings, self-selected, missing slice fields; confirmation takes weeksFeedback to discover, offline paired experiments to decide, online to confirm
Changes no grader measuresFor example, responses quietly become more formal, or stop asking clarifying questions — every gate still passesPeriodically diff output distributions to find what the instruments miss
